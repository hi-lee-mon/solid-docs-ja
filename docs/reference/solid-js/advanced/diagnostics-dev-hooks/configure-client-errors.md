グローバルなクライアントエラーフックを登録します。エラーバウンダリがフォールバックをレンダーする際にエラーオブジェクトごとに 1 回呼び出され、エラーがスローされた場所と捕捉された場所が渡されます。

## 関連する型

### `ClientErrorContext`

クライアントエラーフックは本番層（prod 層）に設けられた接続点で、アプリやエラーモニターが、他のどこからも見えない唯一の失敗、つまりエラーバウンダリ（`createErrorBoundary`、`<Errored>`）がエラーを捕捉してフォールバックをレンダーしているケースを受け取るためのものです。
ブラウザのグローバルハンドラーが受け取るのは `window.onerror` に届いたものだけであり、レンダーされたフォールバックはそこには届きません。
捕捉されなかった（UNCAUGHT）エラーはこのフックの対象ではありません。停止（`REACTIVITY_HALTED`）はその原因をプラットフォームの `reportError`、つまりすべてのモニターがすでにリッスンしているチャネルへ渡します。イベントは 2 つではなく 1 つです。

エラーオブジェクトごとに 1 回だけ呼び出されます。バウンダリの `reset()` が同じ失敗したノードを再計算して同じエラーを再び捕捉しても、再び報告されることはありません。
層は 2 つあります。グローバルな層（`configureClientErrors`）とルートごとの層（`@solidjs/web` の `render`/`hydrate` の `onError`）で、最も近いルートが優先されます。
どの層でも発火します。戻り値はありません。クライアントには対応付けるべきワイヤー上の表現がないためです。
`ownerPath` には、ランタイムがオーナー名を保持しているビルド（observe ビルドと dev ビルド）で、コンポーネントのラベルが入ります。

必要なときだけコストがかかる設計です。このモジュールがバンドルに残るのは `createErrorBoundary`（ここに報告します）を使うか、アプリ自身が `configureClientErrors` をインポートした場合だけです。
ルートのフックは登録済みシンボル（スケジューラーで定義される `ROOT_ERROR_HOOK`）の下でルートオーナーに置かれるため、`render` は何もインポートせずにそれを書き込めます。フックを設定せずバウンダリもレンダーしないアプリには、このコードは一切含まれません。

```ts
interface ClientErrorContext {
  ownerPath?: string[];
  boundaryPath?: string[];
};
```

#### `ownerPath`

- **型:** `string[]`

エラーがスローされた場所です。スローした計算のオーナーチェーンをルートから順にたどったラベル（コンポーネントのラベルと名前付きプリミティブ）で、ランタイムがオーナー名を保持しているビルド（observe ビルドと dev ビルド）で利用できます。
スロー元が不明な場合（どの計算にも属さない場所でスローされた値）は、バウンダリ自身のチェーンが入ります。

#### `boundaryPath`

- **型:** `string[]`

エラーが捕捉された場所です。そのエラーに対してフォールバックをレンダーした `<Errored>` のチェーンを、同じ形式のラベルでたどったものです。`ownerPath` が壊れた場所を示すのに対し、こちらはユーザーが見たものを示します。

### `ClientErrorHook`

```ts
type ClientErrorHook = (error: unknown, context: ClientErrorContext) => void;
```

### `ClientErrorsConfig`

```ts
interface ClientErrorsConfig {
  onError?: ClientErrorHook;
};
```

#### `onError`

- **型:** `ClientErrorHook`

フック、または解除するための `undefined`。
