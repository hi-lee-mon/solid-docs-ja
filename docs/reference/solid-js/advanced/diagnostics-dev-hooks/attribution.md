`solid-js/attribution` のアトリビューションエンジンです。`enable()` でインストールし、`subscribe()` を通じて確定したインタラクション・ナビゲーション・ホールド・再実行レコードを読み取り、`costs()`・`feedback()`・`why()`・`subscriptions()` で畳み込みます。プロダクションビルドでは不活性です。

```ts
import { attribution, costs, feedback, formatOrigin, formatRerun, subscriptions, why } from "solid-js/attribution";
```

## `feedback`

ホールドと各再実行上のインタラクションから畳み込んだ、「ユーザーが
何を待たされたか」です。`sources` は非同期ソースを、書き込みがその背後で
保留されたまま過ごした無応答時間順にランク付けし（どのアフォーダンスが
応答したか、どれくらいの頻度か、どのインタラクションが保留されたかを含む）、
`interactions` はユーザーイベントを、それらが要した総時間――引き起こした
再実行作業（ロングフラッシュの危険）と保留された時間（サイレントホールドの
危険）の双方――でランク付けします。あらゆる時間幅での事実であり、
SILENT_HOLD はしきい値を適用した判定です。さらに3つのテーブルが全体像を
補完します。`navigations` はルートを、そこへのナビゲーション中に保留されて
過ごした時間順にランク付けし（確定したナビゲーションから畳み込み）、
`flights` は各非同期ソースのフライト数と着陸前に放棄された数を数え
（再要求ストーム）、`fallbacks` は各ローディングバウンダリがフォールバックを
表示していた時間と、それがフラッシュだった頻度を計測します。

### 型シグネチャ

```ts
function feedback(): AttributionFeedbackTables;
```

## 関連する型

### `Acknowledgement`

画面がホールドに応答した方法の1つです。`reader` はそれが描画された
場所――センサスがそのアフォーダンスを読み取っていることを発見した最初の
エフェクトのオーナーパス（`["<App>", "<Feed>", "effect"]`）――なので、
コンシューマーは「どれかの画面が応答した」だけでなく「どの画面が応答したか」を
言えます。アフォーダンスは登録されたがセンサスがグラフを通じて読み取り側を
見つけられなかった場合は存在しません（楽観的ストア: その読み取り側は
プロキシのトラップであり、ノードではありません）。`feedback()` は
アクノリッジメントを `kind:source`（`isPending:posts`）でランク付けします。

```ts
interface Acknowledgement {
  kind: "isPending" | "latest" | "optimistic" | "affects";
  source: string;
  reader?: string[];
};
```

#### `kind`

- **型:** `"isPending" | "latest" | "optimistic" | "affects"`

#### `source`

- **型:** `string`

アフォーダンスがぶら下がるノード――`isPending`/`latest` では非同期ソース、それ以外では楽観的/影響対象のノードです。

#### `reader`

- **型:** `string[]`

### `Attribution`

エンジンです。オンにして、そのレコードを購読し、そのリングバッファを
読み取ります。それらのレコードに対するフォールド――`costs()`・`feedback()`
――とポイントクエリ――`why()`・`subscriptions()`――とフォーマッター
――`formatRerun()`・`formatOrigin()`――は、ここのメソッドではなく
`@solidjs/signals/attribution` の名前付きエクスポートです。これにより、
レコードだけが欲しいコンシューマー（プロダクションアダプター）は、
コンソールやエージェントが読むテーブルを同梱せずに済みます。フォールドを
インポートすることが、その計上をオンにする操作です。

```ts
interface Attribution {
  enable(opts?: AttributionOptions): void;
  disable(): void;
  subscribe(listener: (event: RerunEvent) => void): () => void;
  subscribe<K extends AttributionRecordType>(
    type: K,
    listener: (record: AttributionRecords[K]) => void
  ): () => void;
  history(): readonly RerunEvent[];
  waterfalls(): readonly WaterfallRecord[];
  holds(): readonly HoldEvent[];
  navigations(): readonly NavigationEvent[];
  interactions(): readonly InteractionEvent[];
  markFlight(flight: object, startedAt?: number): void;
};
```

#### `enable`

- **型:** `void`

#### `disable`

- **型:** `void`

#### `subscribe`

- **型:** `() => void`

レコードを完成と同時に配信します――`AttributionRecords` を参照。
素の形式は `subscribe("rerun", …)` です。レコードはリングバッファが保持する
のと同じオブジェクト（`history()`、`interactions()`、`holds()`、
`navigations()`）であり、エンジンから同期的に配信されるため、リスナーは
シグナルを書き込んではいけません。すべての購読は `disable()` で破棄されます。

#### `subscribe`

- **型:** `() => void`

#### `history`

- **型:** `readonly RerunEvent[]`

#### `waterfalls`

- **型:** `readonly WaterfallRecord[]`

enable() 以降に観測された、グラフから証明可能な逐次フライトチェーンの
すべてです（history() と同様にリングバッファ化）。判定ではなく事実です:
チェーンは時間幅ゲートに関係なく記録されます――ASYNC_WATERFALL 診断が
同じデータへのしきい値付きビューです。

#### `holds`

- **型:** `readonly HoldEvent[]`

enable() 以降に、少なくとも1つのルート書き込みをステージした、確定した
トランジションホールドのすべてです（history() と同様にリングバッファ化）。
判定ではなく事実です: 時間幅や応答の有無に関係なく記録されます――
SILENT_HOLD 診断は、しきい値を超えた無応答の部分集合です。

#### `navigations`

- **型:** `readonly NavigationEvent[]`

enable() 以降にルーターが `withOrigin` を通じて宣言したナビゲーションの
すべてです（history() と同様にリングバッファ化）。確定の有無にかかわらず:
どのルートか、どのインタラクションの下か、何件の書き込みか、そして――
その書き込みが完了した後は――どれくらいかかったかとどう完了したか
（通常のドレインでの `committed`、HoldEvent が付随するルートデータの背後での
`held`、着陸前に後のナビゲーションに取って代わられた `superseded`）。
ルート名でナビゲーションのスパンが欲しいあらゆるコンシューマー向けの
事実です: ルーター統合は不要です。

#### `interactions`

- **型:** `readonly InteractionEvent[]`

enable() 以降にランタイムが `withInteraction` を通じて宣言した
ユーザーインタラクションのすべてです（history() と同様にリングバッファ化）。
確定の有無にかかわらず: 何がディスパッチされたか、いつか、何を書き込んだか、
引き起こした再実行と生成、その書き込みが待ったホールドと実行した
ナビゲーション――そして、それらすべてが完了した後は、その人がどれくらい
待ったか（`settledMs`）とどう終わったか（`idle` / `committed` / `held`）。
ディスパッチごとのこのレコードを `feedback().interactions` が名前で
畳み込みます。

#### `markFlight`

- **型:** `void`

協調的なプリロード宣言です: リアクティブグラフが見る前に、フライト
オブジェクト（Promise または非同期イテラブル）にその本当のキックオフ時刻を
スタンプします。ルートプリローダーやクエリキャッシュは、渡す Promise に対して
これを呼び出します（元のキックオフ時刻とともに、自分が作ったラッパーに対して
――ラッピングしないと同一性追跡が破綻します）。後でそれを await する
依存関係は、本当の開始時刻に対して判定されます――上流が着陸した時点ですでに
空中にあった仕事は並列であり、ウォーターフォールのリンクにはなりません。
attribution が無効な間も呼び出せます（ナビゲーション時に付けられた
マークは、後の enable() を越えて生き残る必要があります）。

### `AttributionHooks`

:::deep-dive[AttributionHooks のメンバー]
リアクティブコアのオブザーブ層フックポイントです。

コアの義務は、これらが起きた瞬間に真の事実をもって呼び出すことです。
すべての attribution セマンティクス（スタンプ、原因チェーン、タイミング、
警告）は、これらをインストールするエンジン――
`@solidjs/signals/attribution`――にあります。これは別エントリーであり、
それを有効にしないオブザーブビルドはそれを同梱しません
（GlobalQueue._* 機能スロットと同じパターン）。`attrHooks` はエンジンが
インストールされない限り null なので、無効時のコストはサイトごとの1回の
null チェックであり、prod ビルドはすべてのサイトを __OBSERVE__ の後ろに
畳み込みます。

呼び出し側の実装者にとって重要: フック呼び出しは `try` ブロックの中に
置いてはいけません――rollup の tryCatchDeoptimization は `try` の中で
参照される関数を、畳み込まれた __OBSERVE__ ガードの後ろでも保持し、
エンジンが prod バンドルに再結合されます（#2883 ハーネス）。try の中で
ローカルフラグを立て、catch の後でフックを呼び出してください。

```ts
interface AttributionHooks {
  interactionStart(ref: InteractionRef): void;
  interactionEnd(): void;
  originStart(ref: OriginRef): void;
  originEnd(): void;
  flushEnd(): void;
  recomputeStart(el: Computed<any>, create: boolean): void;
  recomputeEnd(
    el: Computed<any>,
    create: boolean,
    changed: boolean,
    optimistic: boolean,
    transition: boolean,
    held: boolean
  ): void;
  derivedChanged(el: Computed<any>): void;
  write(el: Signal<any> | Computed<any>, prev: unknown, value: unknown): void;
  refreshed(el: Computed<any>): void;
  flightStart(el: Computed<any>, flight: object): void;
  asyncStart(el: Computed<any>): void;
  asyncEnd(el: Computed<any>, prev: unknown, value: unknown, direct: boolean): void;
  effectRunStart(el: Computed<any>): void;
  effectRunEnd(el: Computed<any>): void;
  actionStepStart(it: object, name: string | undefined): void;
  actionStepEnd(it: object): void;
  holdStart(t: Transition): void;
  holdEnd(): void;
  transitionSettled(t: Transition): void;
  transitionMerged(target: Transition, outgoing: Transition): void;
  storeReplaced(
    path: string,
    isArray: boolean,
    total: number,
    unchanged: number,
    prevTotal: number,
    owner: Owner | null | undefined
  ): void;
  listChurn(
    el: Computed<any>,
    removed: unknown[],
    created: unknown[],
    newLen: number,
    keyed: boolean
  ): void;
  boundaryFallback(boundary: object, tree: Computed<any> | undefined, shown: boolean): void;
  currentOrigin(): ChangeOrigin | undefined;
};
```

**`interactionStart`** — `void`

`withInteraction` がユーザーインタラクションフレームを開きました:
対応する `interactionEnd` までのルート書き込みは `ref` のハンドラーが
実行したものです。フレームは厳密にネストするため（同期的ディスパッチ）、
エンジンはスタックを保持します。

**`interactionEnd`** — `void`

**`originStart`** — `void`

`withOrigin` が宣言済み起点フレームを開きました: 対応する `originEnd`
までのルート書き込みは `ref` が記述する作業単位（ルーターの
ナビゲーション）です。インタラクションフレームの内側にネストする
（ナビゲートするリンククリック）ことも、単独で立つ（アクションからの
リダイレクト、プログラマティックな `navigate()`）こともあります。
フレームは厳密にネストするため、エンジンはスタックを保持します。

**`originEnd`** — `void`

**`flushEnd`** — `void`

`flush()` のドレインが完了しました: 処理した各バッチは、コミットされた
（そのエフェクトが実行された）か、保留中の更新にパークされた
（そのために `holdStart` が発火した）かのどちらかです。ドレインごとに
1回、ループの後に発火します――バッチごとではなく、何もすることが
なかった `flush()` 呼び出しでは発火しません。どのトランジションにも
保留されなかった書き込みについて、「コミット済み、画面更新済み」の瞬間を
エンジンに与えます。

**`recomputeStart`** — `void`

再計算が始まります。`el._deps` はまだ前回の実行のリンクを保持しています。
常に `recomputeEnd` と対になります（再計算に早期リターンはありません）。

**`recomputeEnd`** — `void`

再計算が完了しました。`changed` = 変更された値をコミットした（エラーに
なった実行では false）。`optimistic` = 楽観的レーン / レーンダーティ
態勢の下で実行された。`transition` = トランジションがアクティブだったか
このノードを所有している。`held` = 値が直接コミットされるのではなく
`_pendingValue` に入った（トランジションホールド）――その公開は後で
トランジション自身のスケジュールで行われます。

**`derivedChanged`** — `void`

エフェクト以外の computed が再実行中に変更された値をコミットしました。

**`write`** — `void`

シグナルの書き込みがコミットされました（値が等価性ゲートを通過）。

**`refreshed`** — `void`

Refresh() がこのノードを無効化しました（自己無効化、依存関係の変更なし）。

**`flightStart`** — `void`

新しい非同期フライトがシステムに入りました（`el` の再計算中に
`_inFlight` が代入された）。常に所有する再計算の内側で発火します――
両方の呼び出し経路（コアの再計算とプロジェクションの自己登録）は
その内側で実行される――ので、エンジンは現在のフレームスタックを読んで
フライトをそれを引き起こした変更にリンクできます（ウォーターフォール
チェイニング）。`flight` は登録された thenable/iterable そのものです:
エンジンはその同一性をキーにした初見の起点レジストリを持つため、
共有された Promise やプリローダーがマークした Promise は、グラフが
それらを見た瞬間ではなく本当の開始時刻を携えます。

**`asyncStart`** — `void`

非同期ランディングがその値を適用しようとしています（あらゆる分岐の前）。

**`asyncEnd`** — `void`

非同期ランディングが完了しました。`direct` = ランディングが値を
自身で適用した（レーン/オーバーライド経路）。false = setSignal を
通ったもので、その `write` フックがすでにコミットされた変更を
見ています。ランディングがコミットしたかどうかにかかわらず発火します
――呼び出し側はその事実を try ブロックの外に持ち出せないため
（上記の try ルールを参照）、エンジンは asyncStart のスナップショットに
対するノードの状態からコミット済みかを導出します。

**`effectRunStart`** — `void`

エフェクトの命令的な半分（そのエフェクトコールバック）が実行されようと
している / 実行されました。両方とも実行の try の外側で発火します。
`effectRunEnd` はコールバックがスローしたかどうかにかかわらず発火します。
この2つの間の書き込みはそのエフェクトのものです。

**`effectRunEnd`** — `void`

**`actionStepStart`** — `void`

`action()` ジェネレーターの1つの同期ステップが実行されようとしている /
実行されました（次の yield までの `it.next()`/`it.throw()`）。`it` は
その呼び出しのイテレーター――ステップをまたいで安定した同一性を持ちます。
`name` はジェネレーター関数の名前です。この2つの間の書き込みはその
アクションのものです。

**`actionStepEnd`** — `void`

**`holdStart`** — `void`

フラッシュが `t` を未完了と判定しました（transitionComplete の false
判定）: その書き込みはステージング状態のままで、キューはまもなく
パークされます。このフラッシュのレーンエフェクト（可視の応答者――
isPending コンパニオンや楽観的値）が実行される前に発火します。
`holdEnd` はその後のルートの stashQueues 呼び出しから発火するため、
この2つの間のエフェクト実行はホールド*中に*描画した実行です。

**`holdEnd`** — `void`

**`transitionSettled`** — `void`

`t` が完了と判定されました（`_done` が反転する前の、transitionComplete の
true 判定）。その保留中の書き込みがコミットする前に発火するため、
`t._pendingNodes` はまだステージされたものを列挙しています。

**`transitionMerged`** — `void`

`outgoing` が `target` に畳み込まれました（`outgoing._done = target`）。

**`storeReplaced`** — `void`

ストアのセッターバッチが `path` のコンテナ（例: `store.user`）を
別のものに置き換え（両方とも非 null、配列性は同じ、論理的に同じ
スロットではない）、これは新しいコンテナを古いものと比較した
リーフのセンサスです: 新しい側のリーフ（自身のキー、またはアイテム）は
`total` 個、そのうち `unchanged` 個が以前と同じ値（同一性で判定、
アンラップされた値で比較――オブジェクトのキーはキーで、配列のアイテムは
メンバーシップで比較）、古い側のリーフは `prevTotal` 個です。
64 を超えるリーフを持つコンテナは通知されません。書き込みチャネルの
notify から、書き込まれたキーごとに発火します。置き換えが診断に値する
スプレッドコピーだったかどうかはエンジンが決めます。`owner` はストア
ルートが作成されたオーナーです（記録されていない場合は undefined）:
この所見はストアについてのものであり、誰が書き込んだかではないため、
`OBSERVE.exclude` されたパネルのストアは、その書き込みがどのように
到着しても静かなままです。

**`listChurn`** — `void`

`mapArray` の更新が行の破棄と生成の両方を行いました: `removed` は
行が破棄されたアイテム、`created` は新しい行を得たアイテム、
`newLen` はリストの新しい長さ、`keyed` はキー関数が使われているか
（false = 同一性またはインデックス順）。コミット後に発火します。
そのチャーンが同等のレコードを置き換えたか（不安定な同一性）は
エンジンが判定します。

**`boundaryFallback`** — `void`

ローディングバウンダリがフォールバックの表示を開始（`shown` が true）
または停止しました。`boundary` はバウンダリのキュー（安定した同一性）。
`tree` は構築済みの場合にバインドされる部分ツリーの computed――
最初の表示は部分ツリーがまだ構築中の間に発火することがあります――で、
そのオーナーチェーンがバウンダリを名付けます。ソース集合の遷移
（最初の pending ソースが登録 / 最後の1つがクリア）で発火し、
フラッシュごとではありません。

**`currentOrigin`** — `ChangeOrigin | undefined`

表面上の唯一のクエリです: この瞬間に実行されるルート書き込みが
スタンプされる来歴――最も内側の開いているフレーム（エフェクト
コールバック、アクションステップ、ナビゲーション）、ハンドラーが
実行されている下のインタラクション、あるいは再計算の内側ではそれを
引き起こした変更の起点――該当がなければ `undefined`（外部）です。
エンジンのレコードの横に自分自身の事実を記録するランタイムのための
ものです――`@solidjs/web` の `"call"` レコードは、これから行う
サーバー関数呼び出しをスタンプします――これにより、その事実は
時間ではなく返されたオブジェクトの同一性によって、エンジンの
インタラクションレコードとナビゲーションレコードに結合されます。
:::

### `AttributionOptions`

```ts
interface AttributionOptions {
  log?: boolean;
  stacks?: boolean;
  historyLimit?: number;
  hotRuns?: { count: number; windowMs: number } | false;
  wideDeps?: number | false;
  hotTime?: { budgetMs: number; windowMs: number } | false;
  unstableMemos?: number | false;
  wideWrites?: number | false;
  waterfalls?: { minFlightMs: number } | false;
  holds?: { infoMs: number; warnMs: number } | false;
  longHolds?: { infoMs: number; warnMs: number } | false;
};
```

#### `log`

- **型:** `boolean`

各再実行をコンソールに整形表示します（デフォルト true）。

#### `stacks`

- **型:** `boolean`

各書き込みのユーザースタックフレームを捕捉します――低速です（デフォルト false）。

#### `historyLimit`

- **型:** `number`

`history()` のリングバッファサイズです（デフォルト 200）。

#### `hotRuns`

- **型:** `{ count: number; windowMs: number } | false`

ホットスコープ警告: 1つのスコープが `windowMs` 以内に `count` 回
再実行したら診断を発行します（デフォルト 120回 / 1000ms――意図的に
アニメーションフレームの頻度より上に設定されており、60回/秒の正当な
rAF 駆動スコープがオオカミ少年にならないようにしています）。
`false` で無効化します。

#### `wideDeps`

- **型:** `number | false`

ワイドスコープ警告: スコープの依存関係数がこの値に達したら診断を
発行します（デフォルト 30）――粗い読み取り / ヘルパーリークの
シグネチャです。以後、数がさらに50%増えた場合のみ再警告します。
`false` で無効化します。

#### `hotTime`

- **型:** `{ budgetMs: number; windowMs: number } | false`

時間バジェット警告: 1つのスコープの `windowMs` 内での自己時間の合計が
`budgetMs` を超えたら診断を発行します（デフォルト 8ms / 1000ms――
1フレームの半分を1つのスコープに費やした状態）。`hotRuns` と異なり、
実行回数では捕捉できない「少ないが高価な」スコープを捉えます。
`false` で無効化します。

#### `unstableMemos`

- **型:** `number | false`

不安定出力警告: メモが参照的には新しいが浅い比較では同等の
プレーンオブジェクト/配列を、この回数連続でコミットしたら診断を
発行します（デフォルト 4）。そのようなメモの等価性ゲートは決して
閉じません――すべての購読者が上流の変更ごとに再実行される――ため、
プロファイリング以外では見つけられないファンアウト増幅器になります。
`false` で無効化します。

#### `wideWrites`

- **型:** `number | false`

書き込みファンアウト警告: コミットされたルート無効化（書き込み、
refresh、非同期ランディング）が、この数以上の購読者を持つノードに
到達したら診断を発行します（デフォルト 250）。常時オンの
HUGE_FAN_OUT グラフサイズ警告の、より低い基準のオプトインの兄弟
です。HUGE_FAN_OUT は GRAPH_SIZE_WARN_AT（2000）以上の同種の
書き込みで発火し、この警告はそこで引き継ぐため、1つの書き込みが
両方を携えることはありません。ノードごとに1回で、購読者数が2倍に
増えた場合のみ再警告します。`false` で無効化します。

#### `waterfalls`

- **型:** `{ minFlightMs: number } | false`

非同期ウォーターフォール警告: 上流のフライトが解決した後にしか開始
できなかった非同期フライト（その再計算の原因チェーンが上流の非同期
ランディングに到達し、その起点がそのランディングより後）が、それぞれ
少なくとも `minFlightMs`（デフォルト 50ms）かかった 2 個以上の
フライトの逐次チェーンを形成したら診断を発行します。時間幅ゲートは
グラフが見えないものへの安全弁の1つです: 確定済みのプリロードや
キャッシュヒットは速く解決し、警告しません。進行中のプリロードは
起点によって免責されます: `markFlight()` のスタンプ（と初見の
同一性）は、その仕事が上流のランディングに先行していたことを
証明します――逐次ではなく並列です。2個のチェーンは `info` 重要度で
構造化チャネルのみに発行します（依存するフェッチは本来的な場合があり、
マークされていない外部プリロードは不可視のため）。3個以上は `warn` に
エスカレートしコンソール出力を伴います。`false` で無効化します。

#### `holds`

- **型:** `{ infoMs: number; warnMs: number } | false`

サイレントホールド警告: ユーザーの書き込みが非同期作業の背後で少なくとも
`infoMs`（デフォルト 100ms――RAIL の「即座に感じる」上限）保留され、
かつ画面がその待機に一切応答しなかった場合に診断を発行します――
保留された書き込みやそのブロッカーの下流に `isPending()`/`latest()`
の読み取り側がなく、楽観的値もなく、`affects()` マークもなく、
保留中にレーンエフェクトも描画しなかった場合です。`warnMs`
（デフォルト 200ms――INP の「good」上限）未満では、そのイベントは
参考情報です（構造化チャネルのみ）。それ以上ではコンソールがその
所見を受け取ります。エンジンはペイントではなくコミットまでを
計測するため、すべての数値はユーザーが見たものの下限です。
しきい値は意図的に厳しい側に置かれています。ルート書き込みを
1つもステージしなかったホールド（初期ロード、素の `refresh()`）は
判定されません: ユーザーがしたことで応答されなかったものは
ありません。`false` はホールド追跡全体を無効化します
（`longHolds` を含む）。

#### `longHolds`

- **型:** `{ infoMs: number; warnMs: number } | false`

ロングホールド警告: ホールドの静穏テール――最後に参加した書き込みから
コミットまでの時間――が `infoMs`（デフォルト 500ms）に達したら診断を
発行し、`warnMs`（デフォルト 1000ms、RAIL がユーザーの集中が切れると
する点）からは `warn` になります。最後の参加から計測するため、入力を
受け続けるホールド（タイピング）は存続期間ではなく各待機で判定されます。
この長さのホールドは、応答の有無にかかわらず、古い画面が担うべき
範囲を超えています: 正直な UI はフォールバックであり、それは
`Loading` バウンダリがまだ公開していないか、その `on` prop が
変わった場合にのみ得られます。ホールドが応答されていた場合は
LONG_HOLD として報告され、無応答のロングホールドは、バウンダリの
修復を付記した1つの SILENT_HOLD のままです。`false` で無効化します。

### `ChangeKind`

「この実行はなぜ起きたか」のアトリビューション――
`@solidjs/signals/attribution` の背後にあるエンジンです。

ランタイムはすべてのスコープの完全な依存関係集合をすでに知っており、
このモジュールはそれを表面化します。すべての値のコミットはそのノードに
ChangeRecord をスタンプします（書き込み、非同期ランディング、
refresh() による無効化、または `causes` がルート書き込みまでさかのぼる
派生変更）。計算が再実行されるとき、スタンプがそのノードの前回実行より
新しい依存関係がその原因となるため、各再実行は起点の書き込みまでの
チェーンとして説明できます:

  [why-run] effect "docTitle" ran (run 4)
    ← memo "userLabel" changed (#6)
      ← signal "notifications" write (#5) 2 → 3

このモジュールはアトリビューションのエンジンです: すべてのセマンティクスが
ここにあり、コアから分離されています。`enable()` はコアの狭い
オブザーブ層フックポイント（attribution-hooks.ts）にこれをインストールします。
コアの唯一の義務は、それらのフックを真の事実をもって呼び出すことです。
無効時のコストはフックサイトごとの1回の null チェックです。prod ビルドは
サイトを完全に畳み込みます。コアのどこにもこのモジュールをインポートする
ものはありません――パッケージの `./attribution` エントリー経由でのみ
到達可能なため、それをインポートしないオブザーブビルドはそれを同梱
しません。同じフック面は外部コンシューマー（devtools）のための基盤としても
意図されています――1つの仕組み、2つのフロントエンドです。

```ts
type ChangeKind = "write" | "derived" | "async" | "refresh";
```

### `ChangeOrigin`

ルート変更の来歴: それを実行した命令的フレームです。

- `interaction` — ユーザーイベントハンドラー（web ランタイムは
  `withInteraction` でディスパッチをマークします）。`name` はイベント
  タイプ、`target` はヒットした要素（`button#next "Next →"`）、`at` は
  `performance.now()` クロックでのディスパッチ時刻――あらゆる
  フィードバック遅延の数値が計測される基準です。
- `effect` — エフェクトコールバック（`name` = エフェクト名、`run` =
  そのエフェクトフェーズが書き込みを実行した計算実行、その実行が記録
  されていた場合――これにより書き込みをそれを生成した再実行に
  結合できます）。
- `action` — `action()` ジェネレーターの1ステップ（`name` =
  ジェネレーター名、ある場合）。`await`（`yield` ではなく）の後の
  書き込みは素のマイクロタスクで実行され `external` とスタンプされます
  ――文書化された抜け道です。
- `async` — 非同期ランディング（`name` = フライトが着陸したノード）。
- `navigation` — ルーターのナビゲーションで、ロケーション書き込みを
  `withOrigin` で囲んで宣言されます（`name` = マッチしたルート
  パターン `/users/:id`、`to`/`from` は具体的なパス、`params` は
  パターンがバインドしたもの、`at` は要求された時刻）。ルーター非
  依存の継ぎ目です: 書き込みをラップするどのルーターでも、すべての
  ホールド・再実行・判定でルート名の付いたナビゲーションが得られ、
  エンジンのどこにもルーター固有の知識は要りません。
- `external` — 上記のいずれでもないもの: タイマー、ソケット、
  Promise コールバック、セットアップ。

非インタラクションフレーム上の `interaction` は、そのフレームが
実行されている下のユーザーイベントです――クリックで始まった
アクション、クリックの書き込みが原因で実行されたエフェクト、
クリックが開始したフライトの着陸、リンククリックが行った
ナビゲーション。これにより、すべての下流コストを、それを支払った
インタラクションでキー付けできます。

```ts
interface ChangeOrigin {
  kind: "interaction" | "effect" | "action" | "async" | "navigation" | "external";
  name?: string;
  target?: string;
  at?: number;
  interaction?: ChangeOrigin;
  run?: number;
  to?: string;
  from?: string;
  params?: Readonly<Record<string, string | undefined>>;
};
```

#### `kind`

- **型:** `"interaction" | "effect" | "action" | "async" | "navigation" | "external"`

#### `name`

- **型:** `string`

#### `target`

- **型:** `string`

#### `at`

- **型:** `number`

#### `interaction`

- **型:** `ChangeOrigin`

#### `run`

- **型:** `number`

`effect` のみ: このコールバックが属する計算実行の `RerunEvent.run` です。

#### `to`

- **型:** `string`

`navigation` のみ: 具体的な行き先と出発のパス、およびバインドされた params です。

#### `from`

- **型:** `string`

#### `params`

- **型:** `Readonly<Record<string, string | undefined>>`

### `NavigationRef`

ルーターが `withOrigin` に記述するナビゲーションです。これから実行する
ロケーション書き込みを囲みます。早い段階でマッチさせ、書き込み前に
記述してください: エンジンはその書き込みが引き起こす仕事――ルート
データの背後のホールド、再実行、判定――をこのレコードにキー付け、
パラメーター化されたルートで名付けるため、発生が一緒に畳み込まれます。

エンジンはそのオブジェクトを保持し、ナビゲーションが確定したとき
（およびそれに対するホールドが判定されるとき）に `name`・`to`・
`params` を再度読みます。したがって、書き込み時点でマッチが確定して
いないルーター――ホールドの内側で解決する遅延ルート部分木など――は、
粗く記述し（`/admin/*`）、正確なパターンと params が分かった時点で
同じオブジェクトに代入できます。`from` と `at` はフレームが開くときに
1度だけ読まれます。

```ts
interface NavigationRef {
  kind: "navigation";
  name?: string;
  to?: string;
  from?: string;
  params?: Readonly<Record<string, string | undefined>>;
  at?: number;
  redirect?: number;
};
```

#### `kind`

- **型:** `"navigation"`

#### `name`

- **型:** `string`

マッチしたルートパターン――`/users/:id`。すべてのコンシューマーがグループ化に使う名前です。

#### `to`

- **型:** `string`

具体的な行き先のパスです。

#### `from`

- **型:** `string`

離れようとしている具体的なパスです。

#### `params`

- **型:** `Readonly<Record<string, string | undefined>>`

パターンがバインドしたルート params――`{ id: "42" }`（バインドされなかったオプション params は `undefined`）。

#### `at`

- **型:** `number`

`performance.now()` クロックでナビゲーションが要求された時刻です。
デフォルトは現在時刻です。要求が書き込みより先行するルーター
（ロケーションが動く前にローダーを await する場合）は、ここに自分の
開始時刻を渡します。

#### `redirect`

- **型:** `number`

`>= 1`: このフレームは、まだ保留中のナビゲーションの N 番目の
リダイレクトホップです――ガードやローダーが着陸前に別の場所へ
送ったもの――で、新しいナビゲーションではありません。エンジンは
それをその保留中のレコードに畳み込みます: レコードはユーザーの
要求時刻とインタラクションを保持し、行き先はこれになり、放棄された
行き先は `redirects` に保持されます。畳み込む保留中の
ナビゲーションがなければ、独自のナビゲーションを開きます。

### `RerunEvent`

```ts
interface RerunEvent {
  run: number;
  at: number;
  nodeRuns: number;
  nodeKind: "effect" | "memo";
  nodeName: string;
  nodeId: number;
  causes: ChangeRecord[];
  depCount: number;
  depsAdded: string[];
  depsRemoved: string[];
  selfMs: number;
  totalMs: number;
  changed: boolean;
  phase: "plain" | "held" | "optimistic";
  held: boolean;
  interaction?: ChangeOrigin;
};
```

#### `run`

- **型:** `number`

グローバルな単調増加の実行シーケンスです。

#### `at`

- **型:** `number`

実行が始まった時刻です（`performance.now()` クロック）。

#### `nodeRuns`

- **型:** `number`

attribution が有効になってからこのノードが再実行した回数です。

#### `nodeKind`

- **型:** `"effect" | "memo"`

#### `nodeName`

- **型:** `string`

#### `nodeId`

- **型:** `number`

実行されたスコープの同一性です。プロセス内のノードの存続期間で
安定しています: 1つのメモ/エフェクトのすべての実行は同じ `nodeId`
を持つため、レコードがプロセスを離れた後でも実行をスコープに結合
できます（`nodeName` だけでは、無名の `effect` がすべてマージされて
しまいます）。エンジン自身のノードごとの id であり、`ChangeOrigin.run`
や cycle/relay チェックがキーにするものでもあります。プロセスや
セッションをまたいでは意味を持ちません。生きたノードが欲しい
プロセス内コンシューマーは `OBSERVE.subjectOf(event)` を尋ねます。

#### `causes`

- **型:** `ChangeRecord[]`

このノードの前回の実行以降に変化した依存関係です。空は、再実行が
追跡された値の変化でトリガーされなかったことを意味します
（作成に隣接するプル、エラーの再試行、またはこのプロトタイプがまだ
スタンプしない原因）。

#### `depCount`

- **型:** `number`

この実行後の依存関係数です。

#### `depsAdded`

- **型:** `string[]`

この実行が購読し、前回の実行がしていなかった依存関係の名前です。

#### `depsRemoved`

- **型:** `string[]`

前回の実行が持っていて、この実行が落とした依存関係の名前です。

#### `selfMs`

- **型:** `number`

ネストされた再計算を除く、この実行の壁時計時間です（ms）。

#### `totalMs`

- **型:** `number`

ネストされた再計算を含む、この実行の壁時計時間です（ms）。

#### `changed`

- **型:** `boolean`

実行が変更された値を生成したかどうかです。`changed: false` の
PLAIN なメモ実行は純粋な無駄でした――等価性カットオフが誰にも
通知するのを止めました。エフェクトはコアでは `_equals: false` で
実行されます（そのエフェクトフェーズはすべての再計算で再発火する）
ため、エンジンはこの事実を自分で導出します: 計算出力が前回の実行と
同一であるエフェクト実行は `changed: false` と報告されます――
フェーズは同じ入力で再発火し、純粋な無駄です。副作用のみの計算
（`undefined` 出力）は免除されます: `undefined` の同一性はその
仕事について何も証明しません。costs() では `wastedMs` として合計
されます（plain かつ非 held の実行のみ――`phase` を参照）。

#### `phase`

- **型:** `"plain" | "held" | "optimistic"`

この実行がどの態勢の下で実行されたかです。"optimistic" = 楽観的
レーンの下（オーバーレイ再計算）。"held" = ホールドが開いていたか
そのノードを所有している（実行は後でリプレイ/確定されることがある）。
"plain" = 通常のコミットされた実行。オーバーレイ実行は実際の仕事
です（時間バジェットに計上される）が、無駄として責められることは
なく、costs() はその時間を `overlayMs` として別に報告します。

#### `held`

- **型:** `boolean`

変更された値が直接コミットされるのではなく `_pendingValue` に
パークされ（保留）、その公開はホールド自身のスケジュールで
行われます。保留された実行は無駄の計上から除外されます。

#### `interaction`

- **型:** `ChangeOrigin`

この実行が原因をたどってさかのぼるユーザーインタラクションです。ある場合に存在します。
